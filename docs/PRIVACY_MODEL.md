# Sala Privacy Model

Sala is a synthetic-data prototype for an in-clinic arrival and waiting-room display workflow. It is not a HIPAA-compliant product. It demonstrates HIPAA-minded design decisions for one risk: a public screen receiving more patient information than it needs.

## Premise

Modern intake often happens before the visit through an EHR portal, mobile check-in, or kiosk. Sala focuses on the layer that can still leak information after intake is done: the in-clinic arrival queue and the public waiting-room board.

## Assets

Fields treated as sensitive in this prototype:

- first name
- last name
- full name
- date of birth
- visit reason
- exact arrival time
- internal patient ID

Synthetic fixtures also avoid SSNs, phone numbers, email addresses, addresses, and MRN-like strings.

## Surfaces

| Surface | Audience | Allowed data |
| --- | --- | --- |
| Staff queue | Front-desk staff | Full name, token, glyph, masked DOB, reason, arrived time, wait, status |
| Public board | Waiting room | Glyph, token label, rough wait range, status |
| Case study | Portfolio reviewer | Architecture and test evidence only |

## Risks

- A public board accidentally receives a patient name, DOB, reason, or service label.
- Staff confuse the public display with the staff queue.
- A browser stores patient data after the session.
- A third-party script receives sensitive workflow data.
- A staff screen remains visible after someone steps away.
- A future implementation adds EHR integration and widens the public payload.

## Controls

- `project(patient, surface, now)` denies by default and returns only the fields listed for that surface.
- `getBoardFeed()` serializes `View<"publicBoard">[]` before the board renders it.
- `/board` does not import the store or `Patient` type.
- Unit tests fail if direct patient fields enter the board feed.
- Browser tests verify no localStorage, sessionStorage, IndexedDB, or cookies after a full flow.
- Browser tests fail on third-party requests.
- Staff and check-in screens blur after 60 seconds of inactivity.
- `src/policy/displayContract.ts` names the display contract and the proof behind it.

## Integration Story

In production, Sala would sit beside an EHR or patient-access platform. The server would map appointment and arrival state into a display-safe queue record. The public board would never query the EHR directly. It would receive only a minimum-necessary feed, scoped to a location and generated by a server-side projection policy.

The staff view could link back to the source system for permitted workflows. The waiting-room board would not receive names, DOB, visit reasons, provider names, department names, room names, payment state, insurance state, or free text.

## Limits

- No authentication.
- No backend.
- No real EHR integration.
- No audit log.
- No production security review.
- No claim of HIPAA compliance.

## What Would Need Production Review

- Role-based access control.
- Server-side audit logging.
- Device enrollment for public displays.
- Business associate agreements with vendors.
- Data retention policy.
- Incident response process.
- Security risk analysis.
- Review by privacy, legal, clinical operations, and front-desk staff.
